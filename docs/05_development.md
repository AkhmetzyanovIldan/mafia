# Архитектура (утверждена)

## GameEngine

Главный оркестратор игры.

Отвечает за:

- жизненный цикл игры;
- взаимодействие компонентов;
- вызов RuleEngine;
- вызов GameFlowController;
- обновление GameSession.

GameEngine не содержит игровой логики ролей.

---

## GameFlowController

Отвечает только за переходы между фазами игры.

Не знает:

- ролей;
- способностей;
- правил мафии;
- ночных действий.

Его задача —

управление жизненным циклом фаз.

---

## StateMachine

Хранит текущее состояние игры.

Проверяет допустимость переходов.

Не знает:

- ролей;
- игроков;
- правил;
- таймеров.

Только конечный автомат.

---

## NightActionCollection

Единственная ответственность —

сбор ночных действий игроков.

Не выполняет:

- обработку;
- сортировку;
- приоритеты;
- применение эффектов.

Только хранение.

---

## RuleEngine

Единственное место,

где происходит применение игровых правил.

Именно RuleEngine:

- рассчитывает ночные действия;
- определяет смерти;
- применяет лечение;
- применяет блокировки;
- выполняет проверки;
- определяет результаты;
- проверяет условия победы.

Никакой другой модуль не имеет права выполнять игровую логику.

## Хуки проверки победы (Win Condition Hooks)

1. **Строгая цикличность проверок:**
   - Конечный автомат (`State Machine`) должен вызывать функцию проверки победы (`checkWinConditions()`) строго в двух точках жизненного цикла раунда:
     - В конце фазы `Morning_Resolutions` (после ночных убийств).
     - В конце фазы `Day_Voting` (после подведения итогов голосования и обработки ничьей).
2. **Игнорирование бесконечных циклов ничьих:**
   - Никаких дополнительных эвристик тайм-аутов по количеству ничьих дней не требуется. Смена дня и ночи продолжается до тех пор, пока `checkWinConditions()` не зафиксирует победу одного из кланов.
---

## Backend

Backend не управляет игрой.

Backend:

- принимает сообщения;
- вызывает GameEngine;
- рассылает GameState.

Больше ничего.

---

## Frontend

Frontend ничего не рассчитывает.

Frontend только:

- отображает состояние;
- отправляет действия игрока;
- показывает результаты.

# Правильная ночная механика

Начинается фаза

```
NIGHT
```

Далее

Все игроки,

которые обладают ночной способностью,

одновременно отправляют свои действия.

Все действия сохраняются в

```
NightActionCollection
```

Никакие действия пока не применяются.

После окончания таймера

один раз вызывается

```
RuleEngine.resolveNight()
```

RuleEngine одновременно рассчитывает:

- убийства;
- лечение;
- проверки;
- блокировки;
- остальные ночные эффекты.

После этого:

- обновляются игроки;
- обновляется GameSession;
- проверяются условия победы.

После этого

```
MORNING
```

или

```
GAME_OVER
```

## Архитектурные требования к динамической ночной фазе

Разработка ночной фазы должна строго соответствовать двухэтапной модели:

1. **Разделение таймеров фазы ночи:**
   - Серверный менеджер таймеров (`Timer Manager`) должен последовательно запускать два подэтапа: `NIGHT_CHECKS_TIMER` (для персональных проверок и действий) и сменяющий его `NIGHT_KILLS_TIMER` (для выбора жертв мафиозным кланом).

2. **Атомарная генерация персональных событий:**
   - В отличие от общего расчета утром, действия проверок и уведомлений (лечение, визит любовницы) обрабатываются **моментально** в момент подтверждения игроком или по факту срабатывания триггера.
   - Сервер отправляет персональный `private_action_result` строго конкретному клиенту (`actor` или `target`), не меняя общий публичный `Game State` для остальных игроков.

3. **Обработка AFK и таймаутов:**
   - Если игрок не совершил действие за отведенный таймер активного подэтапа, эффект его роли не применяется (`action_skipped`).
   - Мафия должна прийти к согласию по цели убийства в рамках `NIGHT_KILLS_TIMER`; при отсутствии консенсуса или молчании одного из участников применяются стандартные правила приоритета или пропуск убийства.

## Требования к сетевой синхронизации ночных ходов

1. **Защита от лагов (Grace Period):**
   - Менеджер таймеров на сервере не должен мгновенно закрывать прием действий в ту же миллисекунду, когда истекает визуальный таймер на клиенте.
   - Реализовать техническую задержку (буфер) длительностью `500ms` для учета сетевой задержки (Round-Trip Time).
2. **Client-side Soft-Lock:**
   - Клиент должен блокировать интерфейс выбора (soft-lock) за `300ms` до конца таймера или в момент нажатия кнопки «Подтвердить», отправляя оптимистичный статус на экран («Действие принято, ожидание конца фазы»), чтобы исключить повторные клики при плохой связи.

## Архитектурное поведение при таймаутах (Timeout Handling)

1. **Отсутствие принудительной генерации:**
   - Конечный автомат (`State Machine`) не должен генерировать случайные или «пустые-но-активные» действия (например, автовыбор случайной цели для молчащего мафиози или автоголос днем).
2. **Обработка пустых коллекций:**
   - Если по истечении таймера фазы от игрока не получено сообщение о действии/голосовании, сервер фиксирует статус `action: null` (или `voted: none`).
   - Фаза обязана завершаться автоматически по истечении таймера, независимо от того, прислали ли все игроки свои действия (система опирается исключительно на серверные таймеры, а не на обязательный сбор 100% подтверждений от живых игроков).

## Требования к серверному API переподключения (Reconnection Sequence)

1. **Транзакционный флаг вpayload:**
   - Ответ на событие `reconnect` должен содержать служебный заголовок транзакции (например, `sync_token` или `transaction_lock: true`), если переподключение совпало по времени с серверным расчетом фазы (например, расчет ночи).
2. **Исключение «гонки состояний» (Race Conditions):**
   - Бэкенд должен гарантировать, что в момент отправки снепшота переподключившемуся клиенту все фоновые расчеты (`RuleEngine`) завершены, и клиент получает уже финальное состояние новой или текущей фазы, исключая промежуточные «серые» стейты.

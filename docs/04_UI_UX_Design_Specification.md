# 04. UI/UX Design Specification (MVP)
## Project Mafia

Version: 1.0 (MVP Final)

---

# 1. Назначение документа

Документ определяет окончательные требования к пользовательскому интерфейсу Project Mafia.

Все решения являются обязательными.

Любые изменения UI должны сначала изменяться в документации, после чего могут реализовываться в коде.

---

# 2. Общие принципы

UI предназначен исключительно для отображения состояния игры.

Игровая логика полностью находится в Game Engine.

Frontend никогда самостоятельно не принимает игровые решения.

Основные требования:

- минимальное количество экранов;
- максимальная простота интерфейса;
- отсутствие лишних действий;
- отсутствие промежуточных экранов;
- отсутствие дублирования информации.

---

# 3. Структура приложения

В MVP существует только два основных экрана.

## Экран 1. Главный экран

Назначение:

- создать комнату;
- настроить комнату;
- подключиться по коду комнаты.

После создания комнаты или подключения пользователь сразу попадает за игровой стол.

---

## Экран 2. Игровой стол

Игровой стол является единственным экраном игры.

Используется:

- до начала партии;
- во время партии;
- после окончания партии.

Никаких дополнительных игровых экранов не существует.

---

# 4. Запрещенные экраны

В MVP отсутствуют:

- Lobby;
- экран ожидания;
- экран выбора роли;
- экран выбора команды;
- экран результатов;
- экран окончания игры;
- экран голосования;
- экран ночи;
- экран дня.

Все игровые состояния отображаются внутри игрового стола.

---

# 5. Главный экран

Главный экран содержит только:

- Создать комнату
- Настроить комнату
- Ввести код комнаты

Никаких дополнительных разделов.

Запрещено:

- профиль;
- друзья;
- рейтинг;
- магазин;
- история игр;
- достижения.

---

# 6. Создание комнаты

После выбора создания комнаты пользователь указывает:

- количество игроков;
- роли;
- длительность игровых фаз;
- последнее слово;
- отображение ролей после смерти.

После создания:

- создается комната;
- генерируется код комнаты;
- пользователь сразу попадает за игровой стол.

---

# 7. Подключение к комнате

Игрок вводит код комнаты.

После успешного подключения сразу открывается игровой стол.

Дополнительные экраны отсутствуют.

---

# 8. Игровой стол

Игровой стол — основной экран приложения.

Структура остается неизменной во всех игровых состояниях.

Изменяется только содержимое.

---

# 9. Структура игрового стола

Игровой стол состоит из:

- верхней панели;
- игрового поля;
- центральной информационной области;
- нижней панели управления.

---

# 10. Верхняя панель

Отображает:

- текущую фазу;
- таймер;
- код комнаты.

Положение элементов постоянно.

---

# 11. Центральная область

Используется для отображения:

- игровых сообщений;
- текущей фазы;
- результатов голосования;
- победителя партии.

Модальные окна не используются.

---

# 12. Нижняя панель

Содержит только:

- микрофон;
- динамик;
- выход из игры (если реализован).

На игровом столе отсутствуют:

- настройки;
- регулировка громкости;
- дополнительные меню.

Громкость регулируется исключительно средствами операционной системы устройства.

---

# 13. Игровые места

Количество мест определяется настройками комнаты.

Каждое место содержит:

- аватар;
- имя игрока;
- номер места;
- состояние игрока;
- индикатор голосовой активности.

---

# 14. Состояния места

Поддерживаются следующие состояния:

- свободное;
- занятое;
- жив;
- мертв;
- говорит.

Другие состояния не используются.

---

# 15. Свободное место

Отображается пустое место.

Игрок может занять его до начала партии.

---

# 16. Занятое место

Отображаются:

- аватар;
- имя игрока.

---

# 17. Мертвый игрок

После смерти игрок остается на своем месте.

Интерфейс отображает состояние смерти.

Игрок не удаляется со стола.

---

# 18. Говорящий игрок

Во время речи отображается индикатор голосовой активности.

Дополнительные эффекты отсутствуют.

---

# 19. Назначение мест

Места назначаются исключительно сервером.

После старта партии расположение игроков фиксируется.

Клиент никогда самостоятельно не изменяет расположение игроков.

---

# 20. Состояния игрового стола

Игровой стол отображает следующие игровые состояния:

- ожидание;
- раздача ролей;
- ночь;
- день;
- голосование;
- последнее слово;
- завершение партии.

Все состояния реализуются внутри одного экрана.

---

# 21. Раздача ролей

После запуска игры каждому игроку отображается только его собственная роль.

После окончания отображения автоматически начинается игра.

---

# 22. Ночь

Интерфейс отображает:

- фазу;
- таймер;
- доступные действия роли.

Игроки без действий находятся в режиме ожидания.

---

# 23. День

Отображаются:

- фаза;
- таймер обсуждения.

Активируется публичный голосовой канал.

---

# 24. Голосование

Игрок выбирает одного игрока.

После подтверждения голос изменить нельзя.

---

# 25. Последнее слово

Активен только микрофон исключенного игрока.

Остальные игроки слушают.

---

# 26. Завершение партии

После окончания партии:

- отображается победившая сторона;
- отображаются роли игроков;
- игроки остаются за тем же столом.

Автоматический переход на главный экран запрещен.

---

# 27. Голосовой интерфейс

На игровом столе используются только:

- микрофон;
- динамик.

Voice Service самостоятельно управляет голосовыми каналами.

Frontend только отображает состояние.

---

# 28. Системные сообщения

Используются короткие уведомления.

Сообщения:

- отображаются поверх игрового стола;
- автоматически исчезают;
- не требуют подтверждения;
- не блокируют интерфейс.

---

# 29. Анимации

Используются только для:

- смены фаз;
- выбора;
- получения роли;
- смерти игрока;
- завершения партии.

Требования:

- короткие;
- не содержат игровой логики;
- могут быть пропущены при восстановлении состояния.

---

# 30. Звуки

Используются только:

- игровые события;
- смена фаз;
- подтверждение действий.

Фоновая музыка отсутствует.

---

# 31. Адаптивность

Поддерживаются:

- Mobile;
- Tablet;
- Desktop.

Используется единый интерфейс.

Отдельные версии интерфейса запрещены.

---

# 32. Визуальный стиль

Основная цветовая схема:

- темный фон;
- светлый текст;
- один акцентный цвет.

Акцент используется только для:

- активного выбора;
- активного игрока;
- важных игровых состояний.

Цвет никогда не используется как единственный способ передачи информации.

---

# 33. Архитектурные ограничения

Frontend никогда самостоятельно не:

- определяет победителя;
- переключает фазу;
- назначает места;
- определяет доступные действия;
- вычисляет игровые события.

Все игровые изменения приходят исключительно из Game State.

---

# 34. Требования к UI

Любой UI-компонент должен полностью восстанавливаться только по актуальному Game State.

Компоненты не должны хранить собственную игровую логику.

---

# 35. Требования к переподключению

После восстановления соединения клиент обязан:

- получить актуальный Game State;
- мгновенно восстановить игровой стол;
- не воспроизводить пропущенные анимации;
- не выполнять локальное восстановление игровых событий.

---

# 36. Критические архитектурные ошибки

При разработке запрещается:

- добавлять новые экраны;
- создавать отдельные интерфейсы для фаз игры;
- реализовывать игровую логику на клиенте;
- использовать локальные таймеры как источник игровых состояний;
- определять игровые места на клиенте;
- использовать один общий голосовой канал с клиентской фильтрацией;
- добавлять функциональность, отсутствующую в утвержденном MVP.

---

# 37. Итоговые принципы

- Только два экрана.
- Только один игровой стол.
- UI отображает состояние.
- Game Engine управляет игрой.
- Backend синхронизирует состояние.
- Frontend не содержит игровой логики.
- Любые изменения происходят только после получения нового Game State.
